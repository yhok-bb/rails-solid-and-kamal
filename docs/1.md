# Step 1：【旧・王道構成】マルチコンテナ環境の構築

**目的：** 一世代前の標準的なWebインフラ（役割分散型）の構造を体感する。  
**フェーズ：** ローカル開発

---

## 構成

```
[ブラウザ]
    ▼
[Nginx]        ← リバースプロキシ（静的ファイル配信 / Pumaへの転送）
    ▼
[Puma (Rails)] ← アプリケーションサーバー
    ▼
[PostgreSQL]   ← メインDB
    ▼
[Redis]        ← Sidekiqのジョブキュー（メモリ上）
    ▼
[Sidekiq]      ← 非同期ジョブワーカー
```

すべて別コンテナ（Docker Compose）で起動する。

---

## やること

### ① Docker環境の構築

`Dockerfile` と `docker-compose.yml` を作成し、以下のコンテナが連携して動く状態にする。

- `web`（Rails + Puma）
- `nginx`
- `postgres`
- `redis`
- `sidekiq`

`nginx.conf` を手書きし、Nginxからpuma（`web:3000`）へのリバースプロキシ設定を記述する。

### ② タスク管理CRUDの実装

`Task`（title, body）のScaffoldを作成。PostgreSQLにデータが保存できる状態にする。

### ③ Sidekiq + Redis による非同期処理の実装

タスク作成時に `ProcessTaskWorker`（3秒待機 → ログ出力）を非同期で呼び出す。

```ruby
# app/workers/process_task_worker.rb
class ProcessTaskWorker
  include Sidekiq::Worker

  def perform(task_id)
    sleep 3
    Rails.logger.info "[ChronosHub] Task #{task_id} processed!"
  end
end
```

```ruby
# tasks_controller.rb の create アクション内
ProcessTaskWorker.perform_async(@task.id)
```

## 観察ポイント（寄り道）

### Nginxのログ確認

```bash
docker compose logs nginx -f
```

静的ファイル（CSS/画像）の配信と、動的リクエストのPumaへの転送が別の扱いになっていることを確認する。

### Redisのメモリ監視

```bash
docker compose exec redis redis-cli monitor
```

タスクを作成した瞬間に、RailsからRedisにジョブデータ（JSON）が投げ込まれる様子を目視で確認する。

### Sidekiqダッシュボード

`routes.rb` にSidekiqのWeb UIをマウントし、ジョブがキューに溜まって消化される様子を視覚的に確認する。

```ruby
# config/routes.rb
require 'sidekiq/web'
mount Sidekiq::Web => '/sidekiq'
```
