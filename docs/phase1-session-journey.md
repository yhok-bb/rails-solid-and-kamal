# Phase 1：セッション問題の背景と実験設計

## なぜPhase 1が必要になったか

VPC構築（Phase 0）で2台のVPSが同じDBを共有できる構成になった。
次の問いが生まれる：**2台になったとき、何が壊れるのか？**

最初に壊れるのがセッション。

---

## セッション問題の本質

### 1台のときは問題ない

```
リクエスト → サーバーA（セッション保存）→ 次のリクエストもサーバーA → OK
```

### 2台になると壊れる（条件による）

ロードバランサーはリクエストをラウンドロビンで振り分ける。

```
ログイン → サーバーA（セッション保存）
次のリクエスト → サーバーB（サーバーAのセッションを知らない → 未ログイン扱い）
```

これが起きるかどうかは**セッションをどこに持つか**で決まる。

---

## Railsのセッションストア3種

| ストア | 保存場所 | 2台構成で壊れるか |
|---|---|---|
| cookie store（デフォルト） | ブラウザ（暗号化） | 壊れない |
| memory store | サーバーのメモリ | 壊れる |
| DB-backed session | DB（外部） | 壊れない |

Railsのデフォルトは **cookie store**。セッションデータをブラウザ側に暗号化して持たせるので、どのサーバーが受け取っても同じ秘密鍵（SECRET_KEY_BASE）で復号できる。

つまり**Railsはデフォルトでステートレス**なので、何もしなければ2台構成でも壊れない。

---

## なぜあえて壊すのか

「壊れない」だけを体験しても、なぜ壊れないのかが分からない。

**意図的に memory store に切り替えて壊してから、cookie store で直す**という手順を踏む。
体感を先に持つことで、cookie storeの設計意図が刻まれる。

---

## Rails 8 Authentication Generatorを使う理由

セッション問題を体感するには「ログインして、別サーバーに弾かれる」という体験が必要。
そのためにログイン機能が必要だった。

```bash
bin/rails generate authentication
```

このジェネレーターが生成するもの：

| ファイル | 役割 |
|---|---|
| `app/models/user.rb` | ユーザー（bcryptでパスワードハッシュ） |
| `app/models/session.rb` | セッションレコード（DBに保存） |
| `app/models/current.rb` | リクエストをまたいで現在ユーザーを保持するスレッドローカル |
| `app/controllers/concerns/authentication.rb` | cookieからセッションを探す・作る・破棄する |

Deviseではなく公式ジェネレーターを使う理由：
- Rails 8で標準搭載。依存gemなし
- 生成されたコードがシンプルで読める（SessionモデルがDBに保存される仕組みが見える）
- 学習目的なのでブラックボックスを増やしたくない

---

## 実験の流れ

### Step 1：意図的に壊す

```ruby
# config/application.rb
config.session_store :memory_store
```

この状態で `kamal deploy` して2台構成にする。

### Step 2：壊れることを確認

ブラウザでログインし、リクエストを繰り返す（F5連打 or ロードバランサーが振り分けるまで待つ）。
サーバーが変わった瞬間にログアウト状態になる。

### Step 3：cookie storeに戻して解決

```ruby
# config/application.rb のmemory store設定を削除（デフォルトのcookie storeに戻す）
```

再デプロイしてセッションが維持されることを確認。

---

## cookie storeでも解決できないケース（発展）

cookie storeは「ログアウト強制」ができない。

理由：セッションデータはブラウザ側にある。サーバー側でそのcookieを無効化する手段がない。

例：
- 「全デバイスからログアウト」機能
- アカウント停止処理
- パスワード変更後に他のセッションを即無効化したい

このユースケースには **DB-backed session** が必要。
Rails 8 Authentication Generatorはデフォルトで `Session` モデルをDBに保存する設計なので、ログアウト強制にも対応できる仕組みになっている。

---

## 学習の狙い

| 体験 | 理解できること |
|---|---|
| memory storeで壊す | ステートとスケールアウトの関係 |
| cookie storeで直す | なぜステートレスが強いのか |
| DB-backed sessionの限界を知る | ステートレスにも限界がある場面 |

「ステートレスにしろ」は呪文ではなく、**スケールアウトのためにセッション状態をサーバー外に出す**という設計原則。
